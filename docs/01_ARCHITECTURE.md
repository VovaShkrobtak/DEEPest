# DEEPest — 01. Модульная архитектура и симуляционное ядро

## 1. Технологический фундамент
Godot 4.x (точную стабильную версию закрепить в файлах проекта при старте реализации); типизированный GDScript; при профилировании разрешён нативный модуль или C#-компонент только за стабильным интерфейсом и при подтверждённой совместимости с Android. Целевые сборки Android 10+ и Windows/Linux. UI: Godot Control/Container/Theme; ядро не зависит от SceneTree, Node, Control, CanvasItem и файлового интерфейса.

## 2. Направление зависимостей
UI/CLI/тесты → Application (команды, сценарии использования) → SimulationKernel (время, очередь, транзакции, seed) → доменные модули → типизированное состояние/порты.
Адаптеры persistence, display, localization, logging, data-loader, platform и optional parser реализуют порты, но не становятся зависимостями доменных моделей. Симуляция не знает, что такое кнопка, текстовая строка, локализация или Godot-сцена.

Запретить прямые вызовы одного доменного модуля из глубины другого. Общение через публичные query/command/event-контракты или объявленные обменные потоки. Циклы зависимостей — ошибка CI.

## 3. Рекомендуемая структура исходников
- project.godot; addons/ (только изолированные плагины редактора).
- src/bootstrap/ — композиционный корень, регистрация модулей, конфигурация.
- src/core/ — value objects (Quantity, EntityId), Result, SimulationClock, RNG, EventQueue, EventBus, ModuleRegistry, diagnostics, invariant checks.
- src/application/ — ActionService, ObserverService, SessionService, SaveService.
- src/domain/<module>/ — state, definitions, commands, queries, systems, validators, tests, migration, metadata.
- src/modules/ — необязательные подключаемые доменные пакеты и адаптеры.
- src/content/ — валидируемые JSON/ресурсы контента с версиями схем.
- src/adapters/ — Godot UI, Android, filesystem, persistence, localization, text parsing.
- scenes/ui/ — только UI; tests/unit/, tests/property/, tests/integration/, tests/scenarios/, tests/performance/.
- tools/ — валидация данных, benchmark, seed-replay, миграции, debug.
- docs/ — ТЗ, ADR и формулы; .github/workflows/ — headless CI.

## 4. Контракты сущностей и компонентов
EntityId — стабильный ID, уникальный в мире; entity_kind — вид сущности; components — независимые фрагменты состояния. Сущность может быть телом, обувью, жидкостью, мешком, комнатой, дверью, автомобилем, животным, NPC, сооружением.
Определение (immutable content definition): материал/тип/возможности/параметры по умолчанию. Экземпляр (mutable world instance): ID, фактический состав, масса, температура, влажность, загрязнения, износ, владелец, позиция, связи, история изменений.
Не навязывать идеологический ECS: допускается компонентный data-oriented подход, если он даёт стабильные идентификаторы, выборки, контроль целостности и миграции. Не строить наследование на десятки уровней.
Связи: contains, wears, attached_to, installed_in, located_at, connected_to, owned_by; каждая направленная/парная связь имеет валидатор и правило удаления.

## 5. Модуль — минимальная единица изменений
Каждый модуль объявляет:
- имя, семантическую версию, версию схемы данных, зависимости и разрешённые интеграционные события;
- собственные Definition/State, фабрики, валидаторы и миграции;
- публичные Query (без мутаций), Command (запрос действия), Event (уже свершившийся факт), Advance(delta_seconds, context);
- временной шаг, способ агрегации во сне/при пропуске времени, потребляемые/производимые потоки;
- инварианты, показатели профилирования, юнит-/сценарные тесты.
Недопустимы: чтение приватных полей соседнего модуля, прямое изменение состояния из UI, скрытые глобальные singleton-ссылки, зависимость от строк локализации.

Пример интерфейса по смыслу:
IWorldModule.validate(context) -> issues
IWorldModule.query(snapshot, query) -> data
IWorldModule.handle_command(tx, command) -> Result
IWorldModule.advance(tx, dt_seconds) -> Events
IWorldModule.migrate(old_schema, data) -> Result

Контракт схемы и порядка выполнения — нормативный; имена реальных GDScript-классов могут изменяться через ADR.

## 6. SimulationKernel
- Игра использует монотонное игровое время (целые миллисекунды либо целые секунды; решение фиксировать). Календарь и часовой пояс — отдельная проекция.
- Системы не используют Time.get_ticks_msec() как игровое время. Wall clock используется только для UI/профилирования.
- Действия оформляются как проверяемые транзакции: preconditions → reserve ресурсов → начало → интеграция мира и стадии работы → commit/interrupt/rollback частичной операции → events.
- Для продолжительных действий поддерживаются progress, изменение условий, конкуренция за ресурсы, прерывание, частичный результат, возобновление только если технологически возможно.
- Очередь событий стабильна: (sim_time, phase, priority, sequence_id). Нет зависимости от порядка обхода словаря.
- Формулируется порядок фаз: внешняя среда/погода → потоки среды и конструкций → предметы и материалы → организмы → агенты/решения → действия и изменения → наблюдения/логирование. Для циклически связанных потоков использовать явный итеративный solver или единый шаг обмена с тестом сходимости; не делать скрытое двойное списание.
- Каждое вещественное изменение имеет контекст source, target, transfer, losses, reason.
- Физическое состояние обновляется независимо от открытого UI и без привязки к FPS.

## 7. Время и уровни детализации
Событийная очередь для редких событий; ограниченные шаги для нелинейных быстрых процессов; аналитические или валидированные агрегированные переходы для долгих периодов; event-triggered wakeup для опасных порогов.
При ускорении на часы запрещено просто выполнять один крупный шаг, если он перескакивает кипение/замерзание, потерю сознания, тушение огня, смерть NPC или дефицит кислорода. Алгоритм выбирает безопасный dt по ближайшему событию и точности модельных потоков. Одинаковая траектория при ускорении и обычной игре должна совпадать в заявленном допуске.
Секторы мира: FOCUS (комната и персонаж — точная модель), NEAR (соседние помещения/агенты — средняя), FAR (аналитические запасы, маршруты, статистические процессы). При приближении FAR-развёртка восстанавливает согласованное распределение, не создавая вещество и не переписывая историю.

## 8. Состояние, обмен информацией и детерминизм
WorldState — единственная авторитетная модель. ObserverSnapshot — ограниченная проекция для игрока и UI. KnowledgeState — что персонаж видел, измерил, запомнил или узнал, с погрешностями. AuditTrace — информация разработчика, скрытая в обычной игре.
Каждый subsystem RNG получает детерминированный поток seed+stream_id+entity_id+event_counter; не использовать глобальный randf() без протокола. Случайные величины с заданным распределением и основаниями; реплей = (world_seed, version, config hash, action log).
Ключевые инварианты: уникальные ID; нет отрицательной массы/объёма; сохранение потоков; допустимые составы; одно фактическое место нахождения; ацикличный контейнер; актуальные зависимости; консистентные связи; невозможность провести время назад.

## 9. Единицы и вычисления
СИ внутри ядра: kg, m, s, K, Pa, J, W, mol по необходимости; удобные °C, мл, ккал только в адаптере и определённых конверсиях. Тип Quantity+unit или специализированные value objects, не bare float для несовместимых физических величин.
Интегрирование: ограниченные шаги; устойчивые схемы; точность и сохранение проверяются property-тестами. Округление для текста не меняет состояние. Численные константы версионируются в data/calibration и имеют комментарий об источнике/допущениях.

## 10. Команды и события
Command: command_id, actor_id, target_id(s), verb, parameters, expected_revision, requested_start, optional cancellation; результат: accepted/rejected/deferred, machine-readable reason, duration estimate range, reservations.
Event: immutable event_id, time, type, subject_ids, causal_parent_ids, typed payload, visibility rules, version.
Запись события не равна текстовому сообщению: PresentationRules переводят факты в ощущения/описания, фильтруя по навыку, освещению, сознанию, расстоянию, слуху и языку.
Внешний parser переводит текст → одну или несколько строго типизированных Command; никогда не исполняет произвольный код.

## 11. Модульные границы (owner данных)
- Physiology владеет тканями и физиологическими состояниями; Nutrition поставляет усвоение, Water поставляет свойства жидкости, Environment поставляет тепловые потоки.
- Materials владеет веществами и смесями; Containers — состоянием ёмкостей и переносом; Fire — реакциями горения и теплом; Construction — геометрией и теплопроводностью ограждений.
- Actions управляет жизненным циклом работы, но делегирует последствия профильным модулям.
- NPCDecision владеет намерениями/планами; NPCPhysiology использует тот же физиологический контракт, что игрок, с управляемым LOD.
- WorldGen производит только начальные данные/кандидаты событий и не переписывает существующие факты мира.
Обмен с перечислением потоков и владельца источника исключает дублирование температуры, массы, травм и навыков.

## 12. Совместимость и замены
Сохранять стабильные внешние типы command/event и сериализуемые схемы через версии. Модуль можно отключить только если его зависимости имеют адаптер-заглушку, честно описывающую потерю точности. Внедрение новой формулы требует тестов equivalence/cross-version, миграции при изменении структуры и benchmark. Контент-паки имеют отдельный namespace, deterministic IDs, schema validation. Не исполнять код из контента по умолчанию.

## 13. Требования к observability
Для каждого действия: trace_id, причина, изменённые сущности, дельты потоков, выделение времени, RNG draw tags, ошибки валидации; для расчётных систем: число активных объектов, миллисекунды, количество отложенных событий, ошибки сохранения/баланса.
Debug explorer: дерево сущностей и связей, исходные физические значения, просмотр причин, инспектор дальних зон, шаг времени, реплей, сравнение двух seed, экспорт отчёта. В релизе игрок не видит скрытые данные.

## 14. Опасные антипаттерны
God object Player.gd, тысячи сигналов без owner, UI, напрямую меняющий температуру тела, каждый NPC обновляется каждый кадр, рандом в методе draw, сетка из magic numbers, сохранение через сериализацию сцены, текстовые идентификаторы без namespace, silent catch ошибок, взаимные module imports, необратимые миграции без резервной копии.
