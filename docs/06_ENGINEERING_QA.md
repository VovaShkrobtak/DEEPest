# DEEPest — 06. Данные, сохранения, тестирование, производительность и безопасность

## 1. Качество кода и контракты
- Typed GDScript, явные типы API, понятные имена, единые соглашения единиц и численной точности.
- Чистые вычислительные функции без доступа к Godot Node, времени ОС, локализации и файловой системе.
- Одно ответственное место для мутации каждой доменной величины. Запрещены set_global_heat(), heal_everything() и другие обходы контрактов.
- DI через композиционный корень: зависимости модулей инжектируются интерфейсами и конкретными портами. Автозагрузки (autoload) только в точке старта/обвязке Godot, не как глобальный транспорт данных.
- Контракты, миграции, invariants и sample definitions обязательны при первом создании каждого модуля.
- Важные архитектурные решения фиксировать в docs/adr/: контекст, решение, плюсы/минусы, границы и тесты.

## 2. Источники контента
Контент — версионированные декларативные данные отдельно от расчётного кода. Минимальные каталоги: materials, compounds, item_definitions, part_templates, recipes/processes, buildings, climate_profiles, weather_profiles, organisms, anatomy, traits, diseases (абстрактные классы), flora, fauna, NPC_archetypes, social_rules, settlements, historical_periods, localization, narrative_templates, scenarios.
У каждой записи: namespace:id, schema_version, title_key, tags, units, parameter provenance (source/estimate/assumption), defaults, valid_range, dependencies, migration notes.
DataLoader запрещает дубли ID, недопустимые значения, ошибки единиц, циклы контейнеров, отсутствующие зависимости и несовместимые версии. Тексты и имена не участвуют в идентификации объекта.
Мод-пак не может исполнять произвольный GDScript только потому, что положен рядом с JSON. Скриптовые расширения — отдельный явно разрешаемый механизм с ограничениями и описанием безопасности; в первой архитектурной реализации данные-only.

## 3. Пример формата определений
Минимальный черновой пример, окончательный JSON schema — отдельный версионируемый артефакт:

    {
      "schema_version": 1,
      "id": "core:pine_wood_dry",
      "kind": "material",
      "units": {"density": "kg/m3", "heat_capacity": "J/(kg*K)"},
      "properties": {"density": 500.0, "heat_capacity": 1700.0},
      "parameter_status": {"density": "example_not_calibrated"}
    }

Числа в этом примере — демонстрация структуры, не утверждённые физические значения для реальных пород и влажности. В production использовать атрибуты влажности/породы/температуры и источники.
Для состояния предмета хранить instance_id, definition_id, component schema versions, position, parent/container link, quantity as SI, temperature, composition, damage, contamination, ownership и ревизию.

## 4. Сохранение и восстановление
SaveContainer: format_version, game_build, content_hash, mod_manifest, sim_time, calendar, world_seed, RNG states/counters, WorldState (схемы модулей), ActionQueue, EventQueue, pending transactions, KnowledgeState, journal, config, migration history, integrity checksum.
Atomic write: сначала временный файл → проверка чтения и checksum → атомарная замена основного (с учётом реальных гарантий Android storage) → ротация двух предыдущих рабочих копий. Ошибка записи не уничтожает единственную сохранённую игру.
Сохранять в согласованной точке транзакций; длительные действия сериализуют stage/progress/reservations, чтобы загрузка не дублировала ресурсы. Любая стадия должна пережить save/load с указанным допустимым отклонением.
Миграции схем и контента: отдельные one-way upgrade-функции old→new по версии, идемпотентность чтения, резервная копия, отчёт изменений. Не обещать обратную совместимость произвольных старых сохранений, но изменения схем требуют управляемого обновления и теста.
Состояние удалённого мира и ownership не должно исчезать после загрузки. Генерация региона по seed не должна перезаписывать уже сохранённые мутации.
Экспорт/импорт с проверкой доверенных путей, ограничения размеров и защиты от контента с исполняемыми командами.

## 5. Replay и версионирование
Golden replay содержит seed, build/version, content hash, стартовый state checksum, последовательность команд с временем и параметрами, ожидаемый final checksum и промежуточные state digests по модулям.
Для детерминизма задокументировать: порядок событий, арифметику и округление, политику floating point, генераторы RNG, сортировки, serialization order, интервалы шагов. Межплатформенная побитовая идентичность float необязательна, но целевые численные допуски и одинаковые дискретные исходы обязательны.
Если обновление намеренно меняет физический результат, создать новый reference replay и объяснить расхождения. Незаметное переосмысление сохранённой истории — дефект.

## 6. Тестовая пирамида
- Unit: формулы, преобразования единиц, компоненты, валидация данных, локализация.
- Property-based: неотрицательность, монотонность в контролируемом диапазоне, массовые и энергетические балансы, отсутствие циклов контейнеров.
- Metamorphic: разделение одного события на два эквивалентных шага, масштабирование площади/объёма, перестановка независимых событий, повторная сериализация.
- Integration: кросс-модульные цепочки от действия до физического события и наблюдения.
- Scenario/golden: воспроизводимые истории (08), с эталонными допусками, при одинаковом seed.
- Save/load: старые версии, оборванная запись, незавершённая операция, повреждённая копия, большая база, десять NPC и сто дней мира.
- Fuzz: парсер естественного текста, malformed JSON, лишние/отрицательные значения, неизвестные enum, циклы контейнеров, большие числа, длительные временные прыжки.
- Performance/soak: ночь/месяц, 100+ дней, разные уровни LOD, массовая порча запасов, пожар, массовое перемещение NPC, много журнальных событий, долгосрочные утечки.
- UI regression: адаптивная ширина, 200% шрифт, выдвинутая клавиатура, масштабирование, пустой/переполненный инвентарь.
Любой исправленный баг получает минимальный регрессионный тест. Декларация «готово» без выполнения тестов запрещена.

## 7. CI и требования к коммитам
GitHub Actions при появлении кода:
1) проверить структуру и schema всех content files;
2) запустить headless Godot на зафиксированной версии;
3) lint/type checks, тесты модулей, интеграционные и golden;
4) проверить воспроизводимость и migration fixtures;
5) проверить отсутствие циклов доменных зависимостей и доступа UI→mutable WorldState;
6) собрать Android/desktop на поддерживаемых конфигурациях;
7) сравнить budget benchmarks с baseline, публиковать отчёты;
8) проверка читаемости README/docs и полноты changelog/ADR.
Приложить артефакты при падении: seed, минимальный action log, diff состояний, trace, metrics. Никакой безусловной зелёной сборки при skipped critical tests.

## 8. Производительность: цель и измерение
Базовое устройство для экономных целей: Android 10, ~2 ГБ RAM, слабый CPU/GPU; целевым контрольным примером служит Samsung SM-T515. Цифры ниже — предварительные бюджеты, уточняемые профилированием на реальном устройстве, не обещания готовой сборки.
- Текстовый UI: плавный scroll, целевые 30 FPS даже с длинным журналом.
- Idle Simulation: не более нескольких миллисекунд CPU на игровой тик в обычной комнате; не гонять ядро 60 раз в секунду.
- Простое действие: целевое 95-й перцентиль до 150 мс, сложное локальное — до 400 мс при нормальном объёме мира.
- Ускорение 8 часов отдыха в обычной сцене: ориентир до 2 секунд wall clock с корректным переходом опасных событий; не жертвовать корректностью ради бенчмарка.
- Рабочая память приложения: ориентир <= 250–350 МБ в обычном сеансе на целевом Android; тяжёлые content packs и миры измеряются отдельно.
- Журнал: виртуализация сообщений, дисковые чанки, ограниченные in-memory окна, индексы поиска.
- Инвентарь и модульные данные: sparse representation; не хранить сотни одинаковых уникальных сущностей, если предметы физически неразличимы и допустим стек; при различии состояния не объединять.
- Профиль по CPU, allocations, GC паузам, сериализации, UI draw calls, числу active compartments/agents и сменам LOD.
- Adaptive LOD не должен менять риск смерти, расход запаса и физический баланс сверх допустимых допусков; выявленное расхождение — ошибка модели.

## 9. Нагрузка и экономия
Event-driven вместо постоянного polling; scheduled next_update_time; spatial locality; обработка активной среды пакетами; аналитические решения для линейных и медленных процессов; ограничение частоты решений NPC без замирания мира.
Не кэшировать производные состояния без инвалидации; использовать revision и dependency keys. Не разрешать бесконечную цепную реакцию событий в одном времени без лимита и diagnostics.
Сон и fast-forward — отдельный тестовый режим ядра; нельзя просто вызывать UI-сон в цикле или ускорять wall-clock без расчёта мира.

## 10. Надёжность и безопасность
Игра офлайн по умолчанию: без telemetry, обязательной регистрации или сетевого доступа. Личные сохранения в sandbox приложения; никаких лишних разрешений Android. Контент и строки экранируются для RichTextLabel; пользовательская команда не выполняется через eval, shell или файловые операции.
Защита от save bombs (ограничения количества сущностей/размеров), циклических связей, некорректных migration payloads, невалидных пути/идентификаторов. Критическая ошибка симуляции — fail safely: диагностический report, снимок без частичных мутаций, возможность восстановить последний валидный state.

## 11. Документация модулей и шаблон PR
Новая подсистема обязана иметь:
- design.md: ответственность, допустимые приближения, формулы, источники, зависимости;
- state/definitions schema и version;
- публичные команды/запросы/события с единицами;
- ввод/вывод потоков и критические инварианты;
- тесты normal, boundary, cross-module, replay, save/load, performance;
- локализованные наблюдения/ошибки без утечки скрытого состояния;
- запись в ROADMAP/CHANGELOG и обновлённые docs, если изменился контракт.

## 12. Definition of Done
Функция принята только если: доступна в реальном UI; не нарушает слои архитектуры; имеет физически обоснованную модель и калибровочные допуски; корректно работает при пропуске времени; сохраняется и восстанавливается; имеет regression + integration тесты; диагностируема; работает на Android-контроле производительности; не выдаёт игроку недоступную информацию; меняет мир при повторном посещении соответствующим образом.
